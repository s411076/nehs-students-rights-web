# Local database hardening gate

## Safety and prerequisites

No production connection, secrets, Auth cache, API service or deployment is used.
The runner hard-codes `database-recovery-parity-20261016`, verifies Docker network
`none` and no published ports, and uses `psql -X -h /tmp -U supabase_admin` inside
that container. It **creates a unique DB before any database writes**. `recovery`
is used only as a CREATE DATABASE template and is never migrated or seeded.
The shared-cluster tests reuse only an already isolated executor role and never
broaden its memberships. Retain the recovery
container and its volume. Do not prune it.

The migration is an **existing-schema cutover**, not an empty-project bootstrap.
It requires all nine inventoried UUID-ID public tables and the original columns,
functions and three specifically named endorsements triggers. It deliberately
fails if timestamps are null, displayed proposal counts are null/negative,
the executor role already has unsafe flags/memberships, or the migration has
already been applied. Use a fresh clone for each run. Applying requires a
migration principal able to manage these objects, create the isolated role and
transfer function ownership. The synthetic/restored runs use the recovered
superuser; a separate **fresh-cluster** gate applies as actual non-superuser
`postgres`, with no preexisting executor. Hosted deployment itself remains untested.

## Reproduce

From the repository root, with the retained recovery container running:

```sh
node scripts/database/regression.mjs
node scripts/database/regression.mjs --restored
node scripts/database/managed-principal.mjs
```

The first command creates a clean `template0` DB, loads the minimal Auth schema
(including RLS), the checked-in **schema-only** public baseline and synthetic
legacy fixtures, then applies the migration. The second clones the real restored
schema/data, applies the identical migration, compares original legacy rows inside
SQL without printing them, and tests with synthetic users and synthetic articles.
Each run prints its disposable DB name; DBs are retained so the parent can inspect
or run HTTP gates. Use the **synthetic** DB for any application integration.
Successful runs write sanitized execution evidence to `verification-synthetic.json`
and `verification-restored.json`, containing only DB identifiers, migration hashes, timestamps,
commands and passed gate names (never data or credentials).
The runner never prints SQL result rows or raw PostgreSQL exception messages;
failures expose only SQLSTATE. SQL assertion labels in the source identify intent.

The third command uses the same locally cached image pinned by digest, `--pull=never`,
network `none`, no ports, no mounts of backups/credentials, tmpfs data, and no TCP
listener/background job workers. It copies **password-free roles and Auth/public
schema definitions only** from `recovery`; the prior test executor is excluded.
It seeds only synthetic rows, creates its DB with `OWNER postgres`, and connects
with `-U postgres` for the migration (not a superuser session using SET ROLE).
It checks NOSUPERUSER/CREATEROLE/BYPASSRLS, no ability to SET either managed admin,
Auth ownership, and effective SELECT/REFERENCES privileges and grant options.
The recovered baseline has SELECT WITH GRANT OPTION and REFERENCES **without**
grant option; creating the existing ballot FK requires only REFERENCES.
An Auth-policy negative probe must fail with 42501. A DDL-start event guard verifies
actual `current_user=session_user=postgres` and NOSUPERUSER during construction.
Before/after SHA256 digests compare Auth schema/relation/column/function/default
ACL/policy/constraint catalogs, original row counts and principal attributes.
Full SQL regressions and real SET SESSION AUTHORIZATION denial probes follow;
`verification-managed.json` records sanitized results. The fresh container is
removed in `finally`; neither the source DB nor its existing executor is modified.

`legacy-public-schema.sql` was generated by `pg_dump --schema-only --schema=public
--no-comments` from the untouched disposable recovery clone, not from production.
It contains no table data, emails or credentials. The two intentional bootstrap
adaptations are `CREATE SCHEMA IF NOT EXISTS public` and removal of the dump's
`SET row_security = off`; RLS is not disabled. Re-export only from an untouched
disposable clone, never a migrated DB:

```sh
node scripts/database/regression.mjs --export-baseline rights_test_20261016_7319
```

This baseline is a **test fixture of the unsafe original grants/policies** so the
denial tests prove a change. Never apply the baseline to a deployed project.
Supabase CLI discovery used `npx --yes supabase --help`, `migration --help`, and
`migration new --help`; the migration file was created by
`npx --yes supabase migration new rights_hardening`. No package manifests changed.

## Schema/API decisions

- Migration: `supabase/migrations/20261015183529_rights_hardening.sql`.
  All 22 frozen-contract RPCs return JSON/boolean, not a RightsResult envelope.
  List defaults are 20, maximum 50, limit+1 lookahead; JSON cursor timestamps retain
  microseconds. Query matching is case-insensitive **literal substring**, not SQL
  wildcard syntax, applied before pagination. Missing targeted public items return
  JSON/SQL null; hidden pending/unknown proposals also return null.
- All nine raw application tables deny PUBLIC/anon/authenticated table and column
  privileges; RLS is enabled. Old policies are retained as historical metadata,
  not relied upon for security. New per-operation policies apply **only** to the
  isolated `rights_executor` NOLOGIN/NOBYPASSRLS role. It is not granted to callers.
  No executor Auth SELECT, Auth policy, Auth-schema grant, BYPASSRLS or service key
  is needed. Auth ACLs, owners, policies and RLS state stay unchanged.
- Public wrappers are typed SECURITY DEFINER functions owned by that role, with
  empty search_path and explicitly qualified references. Internal functions live
  in unexposed `rights_private`, with no application USAGE or EXECUTE grants.
  Anonymous callers can execute only public reads and caller-only `rights_is_admin`.
  Other functions require authenticated execution **and** database identity checks.
- The one owner exception is `rights_private.user_identity(uuid)`: postgres-owned,
  STABLE SECURITY DEFINER, empty search_path, static qualified UUID lookup, at most
  one row, returning only email, confirmation/ban/deletion/anonymous state and a
  200-codepoint display label. It returns no raw metadata or Auth composite.
  PUBLIC/anon/authenticated execution is explicitly revoked; only the executor is
  granted execution. Actor validation remains separate so an administrator can
  identify a trusted author who was later banned. All public RPC owners remain
  `rights_executor`. Temporary creator SET/INHERIT membership and schema CREATE
  privileges used for construction are revoked before commit; at most PG17's
  automatic ADMIN-only creator membership remains. Reverse membership is forbidden.
- Eligibility uses the exact recovered `auth.uid()` claim expression + current `auth.users` confirmed full
  `nehs.hc.edu.tw` email, nondeleted/nonanonymous state and a ban that has not expired.
  Expired bans permit access. Caller email uses lower + ECMAScript-compatible trim
  followed by full-domain validation, matching the application. Admin checks compare only that verified email
  to protected `admins.email`; JWT email/role and user metadata are not authority.
  Mutable metadata supplies display labels only, capped at 200 codepoints.
- Existing `user_id` columns are reused. New `attribution_trusted` is false for
  **every** historical row, including those with populated UUID/email/name. Verified
  RPC-created rows alone set true. `rights_admin_author` alone returns trusted UUID
  and email; historical identifiers are returned as `legacy_unverified` with null
  identity fields, not inferred ownership. Public feedback/comments remain redacted
  even for administrators. Admin feedback lists use the same redacted projection;
  identity lookup is separate.
- Proposal `legacy_upvotes_count` copies the displayed `upvotes_count` once.
  Fresh `rights_private.proposal_ballots` has PK `(proposal_id,user_id)`, starts
  empty, and never reads the old votes/endorsements ledgers. Display/receipts derive
  baseline + fresh ballot count, with safe-integer checks; old counter columns stay
  intact. Desired-state votes take a proposal row lock before ledger operations;
  no content-row update means no vote version bump. Ballot user deletion naturally
  reduces the derived total without a stale cache.
- `content_version` starts at 1 on proposals, feedback, comments and home sections.
  Content edits advance it; vote/comment insertion does not update the proposal.
  Moderation requires pending + matching version; all other ID admin writes require
  matching version and comment deletion also matches proposal ID. Unknown historical
  statuses remain untouched; valid new operations enforce the current sets, with no
  global status CHECK that rejects historical rows.
- `rights_private.mutation_history` captures actor/time/full before/after rows in
  the same transaction, including cascading comment deletion; it has no target or
  actor FK so history survives deletion. Vote records capture before/after desired
  state without bumping content versions. Audit identity/content is private.
- NULL proposal/feedback replies alone normalize to empty string; a digest assertion
  verifies substantive replies unchanged before enforcing NOT NULL/default ''. New
  proposal default is `待審核`. All nonnullable RPC arguments reject explicit null,
  lengths use Unicode codepoints and ECMAScript-compatible trim whitespace. Typed
  SQL signatures reject wrong types before function execution. Cursor null is the
  intentional first-page exception; omitted query defaults to '', explicit null fails.
- Expected boundary errors use sanitized PT400/PT401/PT403/PT409 messages. Raw
  table/unsafe-function denial is native 42501; SQL typing/NOT NULL failures retain
  native SQLSTATE, to be mapped deliberately by the backend without exposing messages.

## Legacy inventory and justified changes

The restored public schema has 9 tables, 77 original columns, 4 functions,
3 noninternal triggers, 14 indexes and 25 constraints. All IDs are UUID.
`increment_endorsement(uuid,uuid)` accepts caller-supplied user ID and overwrites
`upvote_count`. The 3 trigger functions update obsolete `endorsement_count` or
`upvote_count` from the old ledger. Only the verified three AFTER endorsements
INSERT/DELETE triggers are retired. Every overload of all four unsafe legacy
functions loses PUBLIC/anon/authenticated execute; functions remain for inspection.
No legacy table/column is deleted. The ambiguous duplicate unique endorsement
constraints/indexes are retained. New indexes cover keyset ordering, per-proposal
comment ordering/FK checks, previously unindexed user FKs, and new ballot user FK;
existing leading-user legacy indexes need no duplicate replacement.

## Coverage and release boundaries

`regression.sql`: direct table read/write denial, RLS/ACL/function-owner checks,
unsafe legacy execute denial (including an extra text overload in the synthetic
baseline), no private-schema access, outsider/unconfirmed/banned/
anonymous/deleted/subdomain-spoof identities, forged metadata/JWT claims, student
vs admin, expired bans, separate trusted/legacy attribution, anonymous projections,
Unicode limits/fallback title, **every** nonnullable RPC parameter as explicit NULL,
malformed cursor/limits/query, baseline/idempotent/cancel votes, pending-only/stale
moderation, stale replies/deletes, content versions, deletion/cascade audit, null
column constraints, and 1,107 tied/microsecond timestamp fixtures per list family.
Pagination traverses beyond 1,000 rows, proves exact order/no duplicates/completeness
and query-filter-before-pagination. The runner adds 8 simultaneous same-user vote
connections, 6 distinct-user connections, cancellation and true→false lock ordering.

`preservation.sql`/`preservation-check.sql` compare all original columns on the four
changed content tables (reply null normalization excepted), verify trusted flags
remain false, baseline totals match and new ballots start empty; results stay in DB.

These are real local PostgreSQL tests, not fake-provider tests. The principal gate
certifies the saved managed role/schema privilege model on a fresh local PG17
cluster, not a live hosted deployment or its current platform event hooks.
They do not certify PostgREST JWT transport, runtime HTTP/UI behavior,
rate limiting, email/provider setup or production cutover. Parent owns HTTP gates.
Auth leaked-password protection is an external conditional gate only if password
login is enabled and the plan supports it; no Auth configuration is changed here.
Production remains gated on a fresh backup, maintenance window and coordinated
application rollout. No commit, deployment or production write is authorized.
